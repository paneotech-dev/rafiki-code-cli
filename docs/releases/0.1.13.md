# rafikicode 0.1.13

Release 0.1.13 makes `rafikicode` check its own work more carefully: it writes down what "done" means before it starts, reproduces a bug before fixing it, notices when it is going round in circles, and catches the errors an edit introduces straight away. It also brings tools for user interface work, images on Rafiki Fast, and two opt-in features: a review before a task is reported as done, and parallel attempts for hard tasks. Every item below is in [CHANGELOG.md](../../CHANGELOG.md) with its detail.

Update:

```bash
rafikicode update
```

Then quit any open window and start it again; `rafikicode --continue` reopens your last conversation.

New install:

```bash
curl -fsSL https://get.rafikiai.io | bash
```

On Windows, in PowerShell (then use Windows Terminal):

```powershell
irm https://github.com/paneotech-dev/rafiki-code-cli/releases/latest/download/install.ps1 | iex
```

## Knowing when a task is done

- **Acceptance criteria.** A task that is not trivial starts with 3 to 5 checkable criteria at the top of the todo list. `review.criteria: false` turns them off.
- **Reproduce first.** A bug report gets a failing test (or a short script) before the fix; the test passes afterwards and is kept.
- **Clearer instructions on the Rafiki tiers.** Every name, text and format the request states is checked before the answer, failures that were there before the change are named rather than "fixed", and the agent changes approach after two equal failures.

## Fewer wasted turns

- **Stuck detection.** The same command failing three times the same way, or edits undoing each other, gets one note to change approach and one line for you. When you have not chosen a tier, the rest of such a turn on Rafiki Fast moves to Rafiki Pro.
- **Errors right after an edit.** The TypeScript and JavaScript, Python and PHP language servers are on by default; an edit gets back only the errors it introduced, within 6 seconds.
- **Checks that are fair to the turn.** A check that was already failing before the turn is named, not sent back for a fix. In a monorepo, the checks of each package the turn touched run in that package.

## User interface work

- **A `screenshot` tool** renders a local page or the project's dev server in the Chrome, Chromium, Edge or Brave you have installed, at desktop and mobile width, and reports overflow, overlaps, low contrast, missing labels and console errors. No browser is bundled.
- **Plan before building.** The first interface request of a session gets a design guide, and the agent proposes a short layout plan before writing code. Say "no plan" to skip it.
- **Rafiki Fast takes images,** so screenshots can be looked at directly; on Rafiki Pro they are described by Rafiki Fast.

## Opt-in

- **Review before done** (off by default): `"review": {"enabled": true}` or `RAFIKICODE_REVIEW=1` has Rafiki Pro check the diff and the check results against the criteria before the task is reported as done, with one more round for what is not met.
- **Parallel attempts** (off by default): `/attempts 3 <task>` or `rafikicode run --attempts 3` tries a hard task two or three ways at once in separate copies of the project, keeps the best one and applies only its change, with one line per attempt giving its checks, diff size and cost.

## Tests

The full `packages/opencode` suite and the interface suite run on the release commit, the release build was measured on the release task set on Rafiki Fast and Rafiki Pro, and the release gate installs, starts, signs in and runs a task on all thirteen builds before anything is published.
