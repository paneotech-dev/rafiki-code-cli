# rafikicode 0.1.8

Release 0.1.8 follows 0.1.7. It fixes a crash in the editor integration: a prompt turn cancelled over the Agent Client Protocol answered an internal error instead of reporting that it was cancelled, which left Zed and JetBrains with a failed request every time somebody pressed stop early. It also tells people more about why a first run went wrong: `doctor` grew from seven checks to ten, the configuration checks now accept exactly what a session accepts, and workspace trust warnings reach the screen instead of a log nobody reads. Existing commands, options, exit codes, the local server and sign in behave as in 0.1.7.

Install or update:

```bash
curl -fsSL https://get.rafikiai.io | bash
```

or, on a machine that already has `rafikicode`, run `rafikicode update`.

## Fixes

- **A cancelled editor turn reports that it was cancelled.** Pressing stop in Zed or JetBrains before the model had produced any token accounting answered the JSON-RPC error `-32603 Internal error: Internal service failure` rather than the `cancelled` stop reason the Agent Client Protocol requires. Two faults were behind it. The usage builder read the message's token counters without checking them, and a turn aborted before the model was called is answered with the user message, which carries no counters at all, so the turn died of a `TypeError`. It now leaves `usage` out for a message with no accounting, which is what that optional field is for: every required field is a total, and zeros would claim the turn is known to have cost nothing rather than that its cost is unknown. Separately, the stop reason was read off that same message, which carries no abort marker either, so a cancellation that did not crash reported `end_turn`. Cancellation is now the agent's own state: the session holds a flag, `session/cancel` sets it before requesting the abort, every turn clears it as it starts, and the turn reads it back as it resolves. Both the early and the mid-stream paths report `cancelled`, and a cancelled turn no longer colours the next one.
- **A defect that kills a turn is written to stderr.** The handler that turns an unexpected failure into a protocol error discarded the original, which is why the crash above left nothing useful anywhere. The client still learns only the safe message, because a defect's text can carry paths and provider detail, and because stdout is the protocol transport.
- **Workspace trust warnings reach the user.** An untrusted workspace loads none of the project plugins, custom tools, local MCP servers, formatters, language servers or permission rules the directory declares, and said so on one line of stderr. In the full screen interface nobody saw it, and under the Agent Client Protocol stderr is a client log file at best. The warning is now the toast the interface already renders, raised both from the worker where project configuration is loaded and from the parent process, and under the protocol it is additionally delivered as an `agent_message_chunk` at the boundaries of a prompt turn. That kind is used because the protocol has no diagnostic method at all and it is the only session update a client is certain to render where the user is looking. The stderr line stays as the fallback. Refusing to run the project's code is unchanged.
- **Events raised before the interface subscribes are no longer dropped.** Global events were discarded when nothing was listening yet, which lost the trust warning above and the notice that a newer version exists. They are buffered and replayed.

## New: doctor checks the project, trust and PATH

`rafikicode doctor` ran seven checks: `config`, `credential`, `gateway`, `key`, `tiers`, `console`, `version`. It now runs ten, in this order: `config`, `project`, `trust`, `credential`, `gateway`, `key`, `tiers`, `console`, `path`, `version`. The three new lines cover first run failures the tool could not previously see.

- **`project`** reads the project configuration a session started in this directory would load: `rafikicode.json`, `rafikicode.jsonc`, `opencode.json` and `opencode.jsonc` from here up to the repository root, plus the same names under `.rafikicode/` and `.opencode/`, listed in the order they merge. `doctor` only ever read the global file, so a malformed file at a repository root was unchecked here and stopped the session at start instead. It is `skip` when `RAFIKICODE_DISABLE_PROJECT_CONFIG` is set, because then nothing loads from the working tree.
- **`trust`** says whether this directory is trusted and by what: `RAFIKICODE_TRUST_WORKSPACE` for this run, or the stored list in `~/.rafikicode/trusted-workspaces.json`. An untrusted directory is a `WARN` and not a failure, because such a run still works, and the note below the line lists what was dropped.
- **`path`** compares the copy of `rafikicode` your shell resolves the name to against the binary running the check, with symbolic links resolved on both sides, so the link the installer makes into a `PATH` directory is the normal passing case. The version check reports the running executable, which is always right and therefore never caught a stale link from an older install or a second copy earlier on `PATH`: the class of failure 0.1.5 set out to fix. A shadowing copy fails here and the fix prints both paths. A launcher script placed on `PATH` by a package manager or a shim based version manager is a `WARN`, because nothing is broken. In a source checkout the process runs from `bun`, so the line reads `skip` rather than guessing.

Both configuration checks now validate against the same decoder the loader itself uses, rather than checking the syntax alone, so `doctor` accepts exactly what a session accepts and a field of the wrong shape is named before anything refuses to start. `doctor` ends with `All checks passed`, naming the warnings when there are any, or `N checks need attention, see the lines marked FAIL.` Exit codes are unchanged: 0 when every line is `ok`, `WARN` or `skip`, 4 when a failed line is a network failure, and 1 otherwise.

## New: installing on Windows and macOS

Both desktop platforms had a release binary published for them and no install route that finished the job.

- **Windows has a native installer.** `install/install.ps1` is the PowerShell counterpart of `install.sh`, which is a POSIX shell script and runs on Windows only inside WSL, Git Bash or Cygwin. It resolves the newest release, picks the build for the machine's architecture, verifies the archive against the published `SHA256SUMS` before writing anything, installs into `%USERPROFILE%\.rafikicode\bin` so that `rafikicode update` recognises the install as the installer's own, adds that directory to the user `PATH` and runs `rafikicode --version` to confirm the binary starts. It needs no administrator rights. It is published as a release asset, so `releases/latest/download/install.ps1` always serves the newest one, the same arrangement `install.sh` uses. Options: `-Version`, `-Prefix`, `-Baseline`, `-NoModifyPath`, `-DryRun`.
- **Windows on ARM can be installed.** `windows-arm64` is built and published with every release, but the installer's list of supported targets left it out, so a Windows on ARM machine running the script under Git Bash was told `unsupported OS or architecture: windows/arm64` while the binary it needed sat on the release page.
- **A macOS account with no `~/.zshrc` gets one.** This was the whole first contact failure on a new Mac. macOS runs zsh and ships no `~/.zshrc`, `~/.zshenv` or `~/.profile` in a fresh account, and `/usr/local/bin` there belongs to root, so the installer could neither write a PATH line into a startup file nor link the binary into a directory already on `PATH`. It printed a line for the user to paste and stopped, which left the binary installed and `rafikicode` not found in that terminal or in any later one. The installer now creates the usual startup file for the shell it detects, `~/.zshrc` for zsh, `~/.bashrc` for bash, `~/.config/fish/config.fish` for fish, and writes the PATH line into it. `--no-modify-path` still writes nothing, and nothing is created when the binary was already linked into a directory on `PATH`, because then the bare name already works.
- **`--binary` keeps the `.exe` suffix on Windows.** `detect_platform` does not run on that path, so a local install under Git Bash wrote the file without the extension, where it does not run.
- **The macOS quarantine attribute is cleared rather than diagnosed.** The installer already explained quarantine when the post-install version check failed. It now removes the attribute before that check, which is what someone installing from an archive they downloaded in a browser needs. A normal install never carries it, because `curl` does not set it.

### What was run, and what was not

The platform selection and the startup file behaviour above were proven on Linux: `install/test-install.sh` stubs `uname` and `sysctl` and asserts the asset each machine resolves to, and every check that asserts a fix was confirmed to fail against the installer as it stood. The signing facts were read out of the published archives rather than inferred.

`install/install.ps1` has not been run. It was written on a machine with no PowerShell, so nothing about it has been executed, not even a syntax check. On Windows:

```powershell
# 1. Syntax only, nothing downloaded or written.
[System.Management.Automation.Language.Parser]::ParseFile("$PWD\install\install.ps1", [ref]$null, [ref]$null) | Out-Null
$PSVersionTable.PSVersion

# 2. Resolve the version and the asset, still writing nothing.
.\install\install.ps1 -DryRun

# 3. Install into a throwaway directory without changing PATH.
.\install\install.ps1 -Prefix "$env:TEMP\rctest\bin" -NoModifyPath
& "$env:TEMP\rctest\bin\rafikicode.exe" --version

# 4. The real thing.
.\install\install.ps1
```

Worth checking in step 4: that the user `PATH` gained one entry and kept the rest, with
`(Get-Item 'HKCU:\Environment').GetValue('Path', '', 'DoNotExpandEnvironmentNames')`; that a newly opened terminal finds `rafikicode`; and that `rafikicode update` reports the installer's own channel rather than refusing. Run step 1 under both `powershell` (5.1) and `pwsh` (7 or later), because they are different runtimes and only the second can test for AVX2.

On macOS, what matters is an account with no `~/.zshrc`, which is a new account rather than a developer's own. Run the script from the checkout, not through `https://get.rafikiai.io`: that address is a redirect to a fixed tag, and until it is repointed it serves an older installer than the one being tested.

```bash
ls -a ~ | grep -E '^\.(zshrc|zshenv|zprofile|bashrc|profile)$'   # expect nothing
bash install/install.sh
cat ~/.zshrc            # expect the PATH line
rafikicode --version    # in a NEW terminal window
codesign -dvvv ~/.rafikicode/bin/rafikicode 2>&1 | grep -i 'Signature\|Identifier'
xattr -p com.apple.quarantine ~/.rafikicode/bin/rafikicode   # expect "No such xattr"
spctl -a -vv ~/.rafikicode/bin/rafikicode                     # expect rejection: not notarised
```

The last two lines are the distinction that matters on macOS: `spctl` rejects the binary because it is not notarised, and it runs anyway because it is not quarantined.

The same applies to the Windows steps: `install.ps1` reaches users through `releases/latest/download/install.ps1`, which serves whatever the newest release carries, so it can only be tested from the checkout until a release carries it.

## Behaviour changes

- **A configuration file that cannot be loaded says what to do about it.** A command that stopped at start with `Configuration is invalid ...` or `Config file at ... is not valid JSON(C)` named the problem and left you there. The message now ends with three fix lines: run `doctor` to see which file is at fault and what to change, the switch that starts one run with nothing from the working tree, and the address of the schema that lists every option with its type.
- **The built in configuration skill is written for this product.** The skill that tells the model how to write a configuration file was hidden, because its text taught file names and a schema address that do not exist here. Hiding it left the hard failure on an invalid file with nothing to prevent it. The replacement carries this product's paths, its schema address, only the tiers people are offered, and the workspace trust rule. Brand values are substituted into the body when it loads, so the branding layer stays the single source of truth.
- **The installer's next steps name `doctor`.** It never mentioned the command that checks whether the install works.

Scripts that match on the earlier wording of these messages need the new text. Exit codes are unchanged.

## Tests

- The Agent Client Protocol agent is now driven against the specification over its real transport, as a real editor drives it: a subprocess over real pipes. The suite covers protocol version negotiation when the client asks for a version that is not supported, cancellation both mid-stream and before the model answers, malformed input (a line that is not JSON, an unknown method, a missing session, parameters of the wrong shape) followed by proof that the connection still works, the first run an editor really sees with no key present, and the trust warning. Every test that reads the stream asserts that each line of it was a JSON-RPC message, so the rule that nothing but the protocol may appear on stdout is proven rather than assumed. The cancellation fix above is the conformance bug this suite found.
- `install/test-install.sh` grew from 16 checks to 30. The twelve new ones cover the desktop platforms. `detect_platform` cannot be exercised by running the installer on the build machine, so `uname` and `sysctl` are stubbed and the resolved asset name is asserted: Apple Silicon, an Intel Mac with and without AVX2, an Intel binary running under Rosetta, Git Bash on x64 and on ARM, and Linux arm64. The rest cover a `HOME` with no shell startup file, which is what a fresh macOS account is.

## Integrity

The installer and `rafikicode update` check each archive against the published `SHA256SUMS`. That is the only integrity guarantee the release makes, and what the operating systems add to it differs by platform:

- **macOS.** The binaries carry an ad-hoc signature with no certificate behind it. That satisfies the rule on Apple Silicon that every executable be signed, so they run; they are not notarised with an Apple Developer ID. Gatekeeper blocks only a file carrying `com.apple.quarantine`, which a browser sets and `curl` does not, so an install through the installer is unaffected while a `.zip` taken from the release page by hand is refused until the attribute is cleared.
- **Windows.** The `.exe` carries no Authenticode signature, so SmartScreen warns on first run.
- **Linux.** No operating system level signing.

An Apple Developer ID with notarisation, and a Windows code signing certificate, both remain to be obtained.
