# rafikicode 0.1.8

Release 0.1.8 follows 0.1.7. It exists for one fix: on a host whose temporary directory is mounted `noexec`, which is usual on shared and cPanel style hosting, `rafikicode` could not start at all. Two users met it, both signed in and billed correctly first, and what they saw was a raw `dlopen` string about a file in `/tmp`. The rest of the release is about the same class of problem: a failure that stops the program before it can tell you anything useful. Startup failures now name a probable cause and a next step instead of printing `Error: Unexpected error`, a cancelled editor turn reports that it was cancelled rather than an internal error, `doctor` grew from seven checks to ten, and the release build now records which of the published binaries were ever started. Existing commands, options, the local server and sign in behave as in 0.1.7. Two new exit codes are described below.

Install or update:

```bash
curl -fsSL https://get.rafikiai.io | bash
```

or, on a machine that already has `rafikicode`, run `rafikicode update`.

## Fixes

- **`rafikicode` starts on a host whose temporary directory is mounted `noexec`.** The full screen interface is drawn by a native library that travels inside the compiled binary. Starting it unpacks that library into the temporary directory and loads it with `dlopen`, so a temporary directory mounted `noexec` takes the write and then refuses the mapping. The failure was total, it arrived after a successful install and a successful sign in, and it read:

  ```text
  Failed to initialize OpenTUI render library: Failed to open library
  "/tmp/.9adb7abbf6e5efff-00000001.so": /tmp/.9adb7abbf6e5efff-00000001.so:
  failed to map segment from shared object
  ```

  The directory comes from `TMPDIR`, but the runtime reads it once while the process starts, so it cannot be changed from inside the program. `rafikicode` now checks, once, whether the temporary directory can run a file, and if it cannot it starts itself again with `TMPDIR` pointing at one that can. It reads `/proc/self/mountinfo` and stops there unless the mount is flagged `noexec`, so a healthy machine pays nothing; when it is flagged, each candidate directory is tested for real by writing a small script, making it executable and running it, because being writable is not the same as being executable and that is the whole bug. The candidates are the cache directory and then the configuration directory, the same convention as everything else this product unpacks for itself. Only a compiled binary is ever restarted, since a run from source unpacks nothing.
- **When no directory can run a file, the message says so, and it is reported as the startup failure it is.** In place of the `dlopen` string the report names `noexec`, lists every directory tried and why each one refused, says that the sign in and the key are not the problem, gives a command to type, and gives a line to send the host. When the temporary directory *can* run a file and the library still failed, `noexec` is not blamed: the message names what is left, a build for another machine or C library, or a memory limit. What the probe found is the probable cause of the startup report described below, which is what carries it: this failure exits 6, prints `Original error:` with every cause behind it, puts the full stack behind `--print-logs`, and offers `doctor` and `run`, exactly as the other startup failures do.
- **The installer checks the same thing.** `--version` does not touch the render library, so the post install check passed on exactly the machines where the first real run was about to fail. The installer now creates and tests the directories the binary would fall back to, reports which one will be used, and warns with the same instructions when none of them works either.
- **A cancelled editor turn reports that it was cancelled.** Pressing stop in Zed or JetBrains before the model had produced any token accounting answered the JSON-RPC error `-32603 Internal error: Internal service failure` rather than the `cancelled` stop reason the Agent Client Protocol requires. Two faults were behind it. The usage builder read the message's token counters without checking them, and a turn aborted before the model was called is answered with the user message, which carries no counters at all, so the turn died of a `TypeError`. It now leaves `usage` out for a message with no accounting, which is what that optional field is for: every required field is a total, and zeros would claim the turn is known to have cost nothing rather than that its cost is unknown. Separately, the stop reason was read off that same message, which carries no abort marker either, so a cancellation that did not crash reported `end_turn`. Cancellation is now the agent's own state: the session holds a flag, `session/cancel` sets it before requesting the abort, every turn clears it as it starts, and the turn reads it back as it resolves. Both the early and the mid-stream paths report `cancelled`, and a cancelled turn no longer colours the next one.
- **A defect that kills a turn is written to stderr.** The handler that turns an unexpected failure into a protocol error discarded the original, which is why the crash above left nothing useful anywhere. The client still learns only the safe message, because a defect's text can carry paths and provider detail, and because stdout is the protocol transport.
- **Workspace trust warnings reach the user.** An untrusted workspace loads none of the project plugins, custom tools, local MCP servers, formatters, language servers or permission rules the directory declares, and said so on one line of stderr. In the full screen interface nobody saw it, and under the Agent Client Protocol stderr is a client log file at best. The warning is now the toast the interface already renders, raised both from the worker where project configuration is loaded and from the parent process, and under the protocol it is additionally delivered as an `agent_message_chunk` at the boundaries of a prompt turn. That kind is used because the protocol has no diagnostic method at all and it is the only session update a client is certain to render where the user is looking. The stderr line stays as the fallback. Refusing to run the project's code is unchanged.
- **Events raised before the interface subscribes are no longer dropped.** Global events were discarded when nothing was listening yet, which lost the trust warning above and the notice that a newer version exists. They are buffered and replayed.

## Startup failures say what went wrong

The top level handler printed `Error: Unexpected error` followed by the error's own message for every failure it did not recognise, and a failure while the module graph was still loading never reached that handler at all. That is how the `noexec` failure above reached a user twice as a raw `dlopen` string.

A startup failure is now classified, and the report names the probable cause with the path or value involved, gives one command to paste, offers the ways out that still work for that failure (`doctor`, and `run`, which needs no render library), and always prints the original error and every cause behind it, with the full stack behind `--print-logs`. The classes are a native library that cannot be mapped, a CPU that refused an instruction, a C library mismatch, no writable directory, a terminal that cannot host the full screen interface, and unknown.

Two classes do not guess. The native library class is diagnosed by the temporary directory probe above, so its probable cause is what the probe measured on that machine rather than what the error text suggests, and the directories it tried are named in the report. An illegal instruction is reported as a bug in the build rather than as the wrong build for the machine: the four archives labelled `baseline` are byte identical to the siblings they exist to replace, as recorded below, and the published build needs no recent instruction set, so there is nothing else for an installer to fetch and the processor it happened on is the thing worth reporting. A terminal that cannot host the full screen interface is named before the renderer loads. The crash handlers are installed as the first import of the program, so a failure during module evaluation is reported the same way instead of as a raw runtime dump.

Two exit codes are new, so an installer or a CI job can tell these apart from not being signed in, which is 2:

| code | meaning |
|---|---|
| 6 | this machine or this build cannot run `rafikicode` |
| 7 | it runs, but this terminal cannot draw the full screen interface |

## doctor checks the project, trust and PATH

`rafikicode doctor` ran seven checks: `config`, `credential`, `gateway`, `key`, `tiers`, `console`, `version`. It now runs ten, in this order: `config`, `project`, `trust`, `credential`, `gateway`, `key`, `tiers`, `console`, `path`, `version`.

- **`project`** reads the project configuration a session started in this directory would load: `rafikicode.json`, `rafikicode.jsonc`, `opencode.json` and `opencode.jsonc` from here up to the repository root, plus the same names under `.rafikicode/` and `.opencode/`, listed in the order they merge. `doctor` only ever read the global file, so a malformed file at a repository root was unchecked here and stopped the session at start instead. It is `skip` when `RAFIKICODE_DISABLE_PROJECT_CONFIG` is set, because then nothing loads from the working tree.
- **`trust`** says whether this directory is trusted and by what: `RAFIKICODE_TRUST_WORKSPACE` for this run, or the stored list in `~/.rafikicode/trusted-workspaces.json`. An untrusted directory is a `WARN` and not a failure, because such a run still works, and the note below the line lists what was dropped.
- **`path`** compares the copy of `rafikicode` your shell resolves the name to against the binary running the check, with symbolic links resolved on both sides, so the link the installer makes into a `PATH` directory is the normal passing case. The version check reports the running executable, which is always right and therefore never caught a stale link from an older install or a second copy earlier on `PATH`: the class of failure 0.1.5 set out to fix. A shadowing copy fails here and the fix prints both paths. A launcher script placed on `PATH` by a package manager or a shim based version manager is a `WARN`, because nothing is broken. In a source checkout the process runs from `bun`, so the line reads `skip` rather than guessing.

Both configuration checks now validate against the same decoder the loader itself uses, rather than checking the syntax alone, so `doctor` accepts exactly what a session accepts and a field of the wrong shape is named before anything refuses to start. `doctor` ends with `All checks passed`, naming the warnings when there are any, or `N checks need attention, see the lines marked FAIL.` Its exit codes are unchanged: 0 when every line is `ok`, `WARN` or `skip`, 4 when a failed line is a network failure, and 1 otherwise.

## Behaviour changes

- **A configuration file that cannot be loaded says what to do about it.** A command that stopped at start with `Configuration is invalid ...` or `Config file at ... is not valid JSON(C)` named the problem and left you there. The message now ends with three fix lines: run `doctor` to see which file is at fault and what to change, the switch that starts one run with nothing from the working tree, and the address of the schema that lists every option with its type.
- **The built in configuration skill is written for this product.** The skill that tells the model how to write a configuration file was hidden, because its text taught file names and a schema address that do not exist here. Hiding it left the hard failure on an invalid file with nothing to prevent it. The replacement carries this product's paths, its schema address, only the tiers people are offered, and the workspace trust rule. Brand values are substituted into the body when it loads, so the branding layer stays the single source of truth.
- **The installer's next steps name `doctor`.** It never mentioned the command that checks whether the install works.

Scripts that match on the earlier wording of these messages need the new text. Existing exit codes are unchanged; 6 and 7 above are new.

## About the published binaries

0.1.7 published twelve binaries, four of them labelled `baseline` for x64 CPUs without AVX2. All four are byte identical to the sibling they exist to replace, because the build toolchain serves one runtime per operating system, architecture and C library, and asking it for a baseline target returns the same runtime under another name. The installer's own detection was never at fault: it reads `avx2` out of `/proc/cpuinfo` and asks for the baseline archive, which is the right thing to do. Nothing could catch it, because the only smoke test ran targets matching the build host, which on the Linux release runner meant the two x64 glibc targets, and those two are the same bytes, so one binary stood in for all twelve.

The release build now smoke tests every target the host can execute, including musl and baseline, hashes every binary and names any targets that produced identical bytes, and publishes `PLATFORM-COVERAGE.md` beside the archives. That file records the host, each target's hash, whether it was started, and why not when it was not, so what has actually been run does not depend on a workflow log that expires. A baseline binary that starts on a host with AVX2 is recorded as proving nothing about the CPUs the variant exists for, rather than as a pass. The collision itself is not fixed by this release; it is now visible and recorded.

## Tests

- The Agent Client Protocol agent is driven against the specification over its real transport, as a real editor drives it: a subprocess over real pipes. The suite covers protocol version negotiation when the client asks for a version that is not supported, cancellation both mid-stream and before the model answers, malformed input (a line that is not JSON, an unknown method, a missing session, parameters of the wrong shape) followed by proof that the connection still works, the first run an editor really sees with no key present, and the trust warning. Every test that reads the stream asserts that each line of it was a JSON-RPC message, so the rule that nothing but the protocol may appear on stdout is proven rather than assumed. The cancellation fix above is the conformance bug this suite found.
- The startup diagnosis tests drive the real binary and assert on what reaches the terminal, including the verbatim `dlopen` failure from the real session, an illegal instruction, a glibc and a musl mismatch, an unwritable home directory and a terminal with no TTY.
- `install/test-install.sh` grew from 16 checks to 18.

## Integrity

Release archives are not code signed. The installer and `rafikicode update` check each archive against the published `SHA256SUMS`.
