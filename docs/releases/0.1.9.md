# rafikicode 0.1.9

Release 0.1.9 follows 0.1.8 by a day and changes the installers only. On a network whose shared IP address had used up GitHub's hourly API allowance, the installer could not find the latest version, reported that the release did not exist, and installed nothing. The `rafikicode` binary is built from the same source as 0.1.8 and behaves the same; if 0.1.8 is installed and working, there is no reason to update.

Install or update:

```bash
curl -fsSL https://get.rafikiai.io | bash
```

or, on a machine that already has `rafikicode`, run `rafikicode update`.

## Fixes

- **The installer works when the GitHub API is rate limited.** To learn the latest version the installer asked the GitHub API, which allows 60 unauthenticated requests an hour for each IP address. Everyone behind one address shares that allowance: an office network, a university, a shared CI runner, a mobile carrier. Once it is used the API answers 403, and the installer stopped with:

  ```text
  curl https://api.github.com/repos/paneotech-dev/rafiki-code-cli/releases/latest exited with status 22.
  That status means the server answered with an HTTP error. For this URL that
  almost always means 404: there is no such file, because there is no such
  release. Check the version you asked for against the published list:
  ```

  No version had been asked for, and the release existed. This was found by installing 0.1.8 from `get.rafikiai.io` in a clean container on the day it was published. The release page is not rate limited and redirects to the newest tag, so `install.sh` and `install.ps1` now read the version from that redirect when the API does not give one.
- **When the version cannot be found at all, the message no longer assumes a 404.** `curl` reports a 403 and a 404 with the same exit status. The message now describes both, says that a rate limited address does not mean the version number is wrong, gives the command that shows the allowance, and says that naming a version with `--version` skips the API. `install.ps1` says the same for `-Version`.

Installing a named version was never affected, because it does not ask the API anything.

## Tests

- `install/test-install.sh` grew from 47 checks to 49. The two new ones run the installer against a local server that answers a real 403 with GitHub's rate limit body and a real 302 from the release page: one asserts that the install completes and prints no `curl` error, the other that with both routes closed the message names the rate limit.
- `install.sh` was also run in a clean container against the real release page with the API address pointed at one that fails, and installed 0.1.8.
- `install.ps1` was run under PowerShell 7.4.2 on Linux in dry run mode for four cases: API refused and release page answering, both refused, API healthy, and the real release page. It has still not run on Windows, and Windows PowerShell 5.1 is a different runtime from the one tested. The fallback uses `System.Net.WebRequest`, which exists on both, for that reason.

## About the published binaries

The archives are rebuilt from the same source as 0.1.8, so their checksums can differ from 0.1.8 while the program does not. `PLATFORM-COVERAGE.md` beside the archives records which targets were started by the release build, as before.
