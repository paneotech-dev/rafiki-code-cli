# Relation to the upstream project

Rafiki Code CLI is a fork. The [attribution section of the README](../README.md#attribution)
names the upstream project and its licence. This page is for maintainers: how
the fork is kept close to upstream, which upstream files it edits and why, and
how an upstream merge is done.

## How the fork relates to upstream

- Upstream is the branch `dev` of `https://github.com/anomalyco/opencode`,
  configured here as the git remote `upstream`.
- Upstream is merged with a real merge commit, never rebased and never
  squashed, so every merge has a merge base and git only reports what changed
  since the last one. Upstream tags are not imported.
- The upstream commit of the last merge is recorded as `base` in
  `script/upstream.json`. Everything on this page is measured against it.
- Package names, import paths, directory names inside `packages/` and the
  `OPENCODE_` environment variables keep their upstream spelling. Renaming
  them would touch every file and make every merge conflict.

## Where the code of this fork lives

| Place | What it holds |
| --- | --- |
| `packages/core/src/brand/` | Names, addresses, defaults, the key guard, workspace trust |
| `packages/opencode/src/rafiki/` | Commands and behaviour of this product: sign in, `doctor`, updates, uninstall, the `gh` commands, gateway errors, resilience, cost |
| `packages/opencode/test/brand/`, `packages/opencode/test/rafiki/` | Tests of the two folders above, and the tests that fail when an upstream name reaches a user |
| `install/`, `docs/`, `schema/` | Installers, documentation, published schema files |
| `.github/workflows/release.yml`, `install-matrix.yml`, `rafiki-vscode.yml` | The workflows this repository runs |

An upstream file should carry at most a call into these folders.

## Rules for a change

1. New behaviour goes into the folders above. The upstream file gets one call
   at the point where the behaviour applies.
2. Text a user reads takes its names from `packages/core/src/brand/brand.ts`.
3. When a whole upstream command or module has to behave differently, write
   the replacement in `packages/opencode/src/rafiki/`, register it instead of
   the upstream one, leave the upstream file exactly as upstream wrote it, and
   list it under `replaced` in `script/upstream.json`.
4. An edit to an upstream file is listed in `script/upstream.json` with its
   class and its reason, and the table below is regenerated:

   ```bash
   node script/upstream.mjs write
   ```

5. A fix that is not specific to this product is offered upstream. Once
   upstream has it, the edit disappears with the merge that brings it in.

The check fails when an upstream file is edited without being listed, when an
entry no longer matches an edit, when a replaced file differs from upstream,
or when the table is out of date:

```bash
node script/upstream.mjs            # the check
node script/upstream.mjs report     # the two figures only
```

It runs as part of `node docs/check.mjs` and of
`packages/opencode/test/brand/upstream-files.test.ts`. A clone without the
base commit, such as a shallow clone, skips it and says so.

The table carries line counts, so a branch that makes an upstream edit larger
shows it in its diff. When two branches both changed the table, do not merge
it by hand: finish the merge and run `node script/upstream.mjs write`.

A replaced file costs nothing at a merge, and that is also its price: a change
upstream makes to it does not arrive by itself. The trial merge below lists
the replaced files upstream changed, so that each change is read.

## Merging upstream

Do this often. A merge of three weeks of upstream work conflicted in eight
files; the cost grows with the distance.

### 1. Look before merging

```bash
git fetch --no-tags upstream dev
node script/upstream.mjs conflicts upstream/dev
```

The second command merges in memory and changes nothing. It prints:

- the files that will conflict, grouped by the classes of the table above,
  with the rule for each class;
- the edited files upstream also changed that merge without a conflict;
- the replaced files upstream changed;
- the workflows upstream added.

### 2. Merge

```bash
git switch -c sync-upstream
git merge --no-ff upstream/dev
```

### 3. Resolve by class

Each class in the table above states its rule. In short:

| Class | On a conflict |
| --- | --- |
| A call into this fork's modules | Take upstream's side, put the call back |
| Product name, file names and wording | Take upstream's side, take the value from the brand module again |
| Behaviour changed in place | Merge by hand, read both sides |
| Tests of upstream, adapted | Take upstream's side, apply this product's expectation again |
| Generated files | Take either side, regenerate after the merge |
| Package identity and packaging | Keep this fork's name, version and binary name |
| Documentation | Keep this fork's text |
| Repository tooling and workflows | Keep this fork's change |
| Editor extension | Keep this fork's side |

A conflict in a file that is on no list means one side changed a file the
record does not know about. Stop and find out which.

### 4. Regenerate

```bash
git checkout --theirs bun.lock
bun install
cd packages/opencode
bun test test/cli/help --update-snapshots
bun dev generate > ../sdk/openapi.json
bun script/schema.ts ../../schema/config.json ../../schema/tui.json
```

Read the diff of each regenerated file before committing it. On a machine
without a compiler use `bun install --ignore-scripts`.

### 5. Read what merged cleanly

A clean textual merge can still change behaviour. Read every file the trial
merge listed as edited here and changed upstream, and every replaced file
upstream changed. Things upstream can undo without a conflict:

- A new string that names the upstream product or one of its commands.
  `test/brand/upstream-names.test.ts` fails on it.
- Seeded defaults: automatic updates and the update source must point at this
  project's releases only.
- `upgrade --method` must offer only the methods this product supports.
- `doctor`, the restart from a temporary directory that cannot run files, the
  ACP cancellation, workspace trust and the key guard.
- The help output. The snapshot test fails on any difference.
- A workflow upstream added or changed must stay inert in this repository.

### 6. Record the new base

Set `base` and `version` in `script/upstream.json` to the upstream commit that
was merged and to its package version, then:

```bash
node script/upstream.mjs write
node script/upstream.mjs
```

Until the base is updated the check reports every upstream change as an edit
of this fork, so this step cannot be forgotten.

### 7. Verify

Run one heavy job at a time.

```bash
bun turbo typecheck --concurrency=3
node docs/check.mjs
cd packages/opencode
bun test test/brand test/rafiki test/cli/help test/installation test/cli/acp test/acp test/config
bun test
```

Then the installer tests (`install/test-install.sh`,
`install/test-install-shells.sh`, `install/test-install-url.sh`,
`install/test-release-gate.sh`) and one binary built for the host, started
with `--version`, `--help`, `doctor` and a rejected flag.

The merge is one branch for review. Nothing is tagged or released by it.
